# FlyBrain Pet — Motor System

## Principle (spec #15, #17, #18, #20, #21)

Movement is **not** brain→animation. It is:

```
brain → motor output → muscles/body dynamics → body motion
      → proprioception → nervous system
```

## Body model (spec #18)

Articulated skeleton:

- head (with eyes, antennae, proboscis)
- thorax
- abdomen
- 6 legs (3 pairs), each with joints: angle, velocity, torque, limits, inertia, damping
- 2 wings (stroke freq/amplitude, L/R asymmetry)
- 2 halteres (inertial feedback — rotation detection, flight stabilization)
- head/neck, proboscis, antennae DOFs

## Motor populations (spec #17)

Motor neurons from connectome (VNC leg neuropils, wing/haltere neuropils,
SEZ proboscis/neck circuits). Where exact muscle-level mapping is unavailable,
a documented **biomechanical approximation** is used — never labeled "exact
biological muscle wiring".

## Locomotion (spec #20)

Six-legged gait is generated by neural pattern generators driven by
**estimates of real firing rate**, not by raw spike counts.

## Drive signal: a rate, not a window count

Two signals are exposed per neuron and they are not interchangeable:

| Signal | Meaning | Use |
|---|---|---|
| `recentSpikes(of:)` | Spikes within the last **1 s of neural time**, a *tumbling* counter cleared wholesale when the window rolls | inspection / raster only |
| `rateHz(of:)` | Leaky estimate of firing **rate** (Hz), updated every step, time constant `motorRateTauMs` | drive for the motor system and any per-step readout |

Using `recentSpikes` as a drive signal was wrong in two separate ways, and both
were real bugs, not cosmetic:

1. **It is not a rate.** A tumbling counter is 0 for most of every window and
   then jumps to the whole window's count, so the value depends on *when* it is
   sampled. A per-step readout would therefore see 0 almost always, with
   occasional lumps — and `activityLevel`, the behaviour classifier and
   `readMotorDrive` all read it that way.
2. **It is far too slow here.** The neural clock runs at 0.1 ms/step and the
   app advances 4 steps per 60 Hz frame: 0.4 ms of neural time per 16.7 ms of
   real time, i.e. **~42× slow motion** (`tools/measure_time_scale.py`). A 1 s
   *neural* window is therefore **~42 s of wall time**, so a fly driven from
   that window could not change its leg drive in under 40 s.

`rateHz` is a conventional leaky rate estimator: each spike adds `1000/tau` Hz
and the estimate decays by `exp(-dt/tau)` every step. Its mean tracks the true
firing rate to within a couple of percent over 20-200 Hz (pinned by
`tools/check_tests.py`); per step it oscillates by design, since a rate
reconstructed from discrete spikes must decay between spikes and jump on each
one.

Drive is reported in Hz and converted once against a single explicit reference
(`SimulationCore.motorDriveReferenceHz`). It previously used three competing
implicit scales — `0.25` per spike for legs, `/6` for the wing and `/4` for the
proboscis — so identical activity meant different things per group.

**Honest limitation.** Because the simulation is ~42× slower than real time, the
fly does not move at fly speed, and the motor loop is not on a real-time
timescale. This is a device budget choice, not a biological claim: at 0.1 ms
per step, reproducing the ~0.8 ms between two spiking neurons at true speed
would need ~8,000 steps per frame on an A13. `AppModel.realTimeFactor` reports
the factor so the UI never implies real-time behaviour.

## Flight (spec #19)

- Wing stroke: frequency, amplitude, L/R asymmetry, thrust/lift reduced-order model
- Body pitch/yaw/roll, takeoff/landing/hover approximation
- Haltere feedback loop for stability
- NOT CFD — biologically plausible control

## Grooming / feeding / escape (spec #21–#23)

All emerge from sensory → neural → motor loops: tactile/odor/gustatory input
modulates neural activity; competing motor programs produce the observed action.
A passive behavior classifier labels what happened **after the fact** (spec #44)
and is never used to drive the fly.
